# v7.17.0 — Borrowed capabilities, wave 3

**Date:** 2026-07-01
**Scope:** feature
**Security impact:** none
**Baseline area:** none (delta touches multiple existing areas without a single baseline owner)

## Context

A competitive scan of Claude Code toolkits created in the last 30 days (June 2026) surfaced 6 candidate capabilities. Cross-checking against the current codebase (dogfooding `prior-work-check` before writing this spec) found that **2 of the 6 are already substantially implemented**:

- Cross-platform config export → `scripts/generate-agents-md.sh` + `scripts/generate-tool-configs.sh` already emit `AGENTS.md`, `.cursor/rules/*.mdc`, `.github/copilot-instructions.md`, `.windsurfrules`, `GEMINI.md`, `.clinerules` from `.claude/references/*.md`.
- Pre-execution visual review of agent loops → `implement/SKILL.md` Phase 2.5 already renders the full batch breakdown (files, acceptance criteria, boundary) and rigor level inline before approval.

For those two, this spec targets the **real gap found on inspection** rather than re-implementing what exists: F1's generators skip CLAUDE.md's Critical Rules section entirely (the one thing a non-Claude-Code tool most needs), and F5's Phase 2.5 rendering shows batches but not the gate/reviewer sequence that will run against them.

The other 4 are genuinely net-new deltas on existing infrastructure (evidence channels, lesson capture, checksums, CODE_INDEX).

## F1 — Critical Rules in generated cross-tool configs

**Problem:** `generate-agents-md.sh` and `generate-tool-configs.sh` concatenate `.claude/references/*.md` but never pull CLAUDE.md's `## Critical Rules` (or equivalently-named) section. A Cursor/Copilot/Windsurf user gets style references but not the "always apply" rules — the highest-value content for a tool with no hook enforcement.

**Fix:** both generators extract the first `## Critical Rules...` (or `## Critical Rules (Always Apply)`) section from the project's `CLAUDE.md` (heading match is prefix-based: `^## Critical Rules`) and place it as the lead section, clearly marked, in `AGENTS.md` and every per-tool config. Absence of a matching heading in `CLAUDE.md` is not an error — emit the rest of the file and skip the section silently (many repos won't use that exact heading).

## F2 — Concrete evidence capture for the `browser` channel

**Problem:** `verification-before-completion.md` defines `browser` as an evidence channel ("Visual or functional check in a browser") but gives no procedure for *persisting* what was seen — unlike `test-run` (test output) or `script-output` (captured stdout), a browser check currently has no artifact, only a claim.

**Fix:** new `.claude/references/evidence-capture.md` documents the capture procedure for the `browser` channel when Playwright MCP tools are available: `browser_take_screenshot`, `browser_console_messages`, `browser_network_requests` are called around the observable behavior, and the results are written under `docs/specs/<slug>.evidence/<criterion-id>/` (screenshot PNG, `console.log`, `network.json`). `verification-before-completion.md` cross-references this procedure and requires the evidence directory path be cited alongside the criterion in the completion table when the channel is `browser`. When Playwright MCP is unavailable, the channel degrades to a plain textual description with that limitation stated explicitly (no silent downgrade).

## F3 — Live golden-path capture (distinct from correction-capture)

**Problem:** `correction-capture` triggers on engineer-issued corrections. `lesson-mining` sweeps past transcripts after the fact. Neither covers the case where the **agent itself** struggles (2+ failed attempts at the same sub-problem) and then finds a working approach, in the current session, with no engineer correction involved — the moment of highest lesson-density is lost unless the session happens to get mined later.

**Fix:** new lightweight skill `golden-path-capture`, distinct trigger from `correction-capture` (self-driven trial-and-error, not engineer feedback). Reuses `correction-capture`'s existing `.claude/lessons/personal.md` / `scripts/learnings.sh` destination and schema — only the trigger and the "wrong_turns" framing differ (this is precisely what `wrong_turns`/`time_cost` fields already exist for). Fires when the agent recognizes: same file/error signature failed 2+ times, then a materially different approach succeeded. Captures immediately, does not wait for Phase 7 or a later mining sweep.

## F4 — Optional cryptographic release signing

**Problem:** `checksums.sha256` (generated by `generate-checksums.sh`, verified by `mtk-doctor.sh`) proves bytes are unmodified but not *who* published them — a tampered fork can regenerate its own checksums.sha256 that matches its own tampered bytes.

**Fix:** `generate-checksums.sh` gains a `--sign` flag. If `MTK_RELEASE_SIGNING_KEY` (path to an Ed25519 PEM private key) is set, it signs `checksums.sha256` with `openssl pkeyutl` (already a hard dependency of this script's sha256sum/shasum fallback story — no new dependency), producing `checksums.sha256.sig`. `mtk-doctor.sh` verifies the signature with `MTK_RELEASE_PUBLIC_KEY` (path to the matching public PEM) when both the `.sig` file and the env var are present; otherwise it reports "release signing not configured" as an informational PASS (never a failing gate — this is an opt-in supply-chain hardening knob, matching the `MTK_READ_GUARD`/`MTK_AUTO_PROCEED` advisory-knob pattern already in the codebase).

## F5 — Gate-sequence preview at Phase 2.5

**Problem:** `implement/SKILL.md` Phase 2.5 already renders the batch breakdown, but not what happens *between* batches — Phase 3.5 drift check, Stage 1/Stage 2 reviewers, iteration cap — so the engineer approves a batch list without seeing the full pipeline that will run against it.

**Fix:** add one short "Gate sequence" block to the Phase 2.5 rendering, computed from the already-known rigor level: `Batches → Phase 3.5 drift check → Stage 1 compliance-reviewer → Stage 2 [test-reviewer + architecture-reviewer[+ silent-failure-hunter at MAX]] → Phase 6 cleanup → Phase 7 compound`. This is a formatting addition to existing Phase 2.5 instructions, not a new gate or new data.

## F6 — Grep-friendly CODE_INDEX query companion

**Problem:** `CODE_INDEX.md` is a static markdown capability table (per `.claude/references/code-index-template.md`). `prior-work-check` and `code-simplification --audit-duplicates` currently grep it ad hoc. A full call-graph is out of scope (no dependency on a language server across every supported stack) — but a small structured query is not.

**Fix:** new `scripts/query-code-index.sh` with two modes:
- `find <keyword>` — greps CODE_INDEX.md's Capability/Entry point/Notes columns, case-insensitive, prints matching rows with their section header (domain).
- `callers <symbol>` — greps the working tree (respecting `.gitignore` via `git grep`) for textual references to `<symbol>`, printing `file:line`. Explicitly a text-reference search, not semantic call-graph resolution — documented as such in `--help`.

`prior-work-check` and `code-simplification` reference the script instead of inlining ad hoc grep.

- Re-implementing cross-platform config export or Phase 2.5 batch rendering (both already exist) — only the identified gaps (F1, F5) are in scope.
