# Instructions Capture

## Current Targets

```!

find . -maxdepth 6 \( -name AGENTS.md -o -name CLAUDE.md \) -not -path "./AGENTS.md" -not -path "./CLAUDE.md" -not -path "./.git/*" -not -path "*/node_modules/*" 2>/dev/null | sort -u
echo "--- Personal (gitignored) ---"
test -f .claude.local.md && echo ".claude.local.md (present)" || echo ".claude.local.md (absent — create for personal-only notes)"
```

## Overview

A session often surfaces context the constitution was missing — a build
command you had to discover, a gotcha you hit, an env quirk, a pattern the
codebase follows. That knowledge should compound into project memory so the
next session starts where this one ended. This skill **reflects on the
finished session**, drafts minimal additions, shows them as diffs, and
applies only what the engineer approves.

Write target precedence: `AGENTS.md` first (the canonical, hand/LLM-authored
constitution), then shims (`CLAUDE.md`, `GEMINI.md`) only for a fact that is
genuinely harness-specific, then nested per-package files for a fact local to
one package. `.claude.local.md` stays the personal, gitignored companion for
first-person preferences — never a shim, never committed.

It is distinct from its two siblings:

- **`instructions-audit`** re-grades what is *already* in the constitution
  against a rubric and fixes rot. Capture *adds new* knowledge this session
  produced.
- **`correction-capture`** records *engineer corrections* as reusable lessons in
  `lessons.md`. Capture records *project facts* (commands, gotchas, env) into
  the constitution — the prompt every session loads.

It honors S1.5 (`AGENTS.md`/`CLAUDE.md` are protected): append-only by
default, `Edit` never `Write`, no additions applied before approval.

## When To Use

- At the end of a session that revealed context the constitution was missing
- When the engineer says "save what we learned", "update AGENTS.md", "update
  CLAUDE.md", "remember this for next time", or invokes the equivalent
  end-of-session capture
- After discovering a non-obvious command, env requirement, or codebase pattern
  that future sessions will need

### When NOT To Use

- First-time repo setup — use `/mtk-setup` (runs `setup-bootstrap`)
- Mid-task — capture at a natural stopping point, not while work is in flight
- Re-grading or fixing stale content — use `instructions-audit`
- Recording an engineer correction — use `correction-capture` (writes a lesson,
  not a constitution fact)
- The session surfaced nothing durable — say so and stop. Do not manufacture
  additions to look useful.

## Workflow

### Phase 1 — Reflect

Review the session. What context, had it been in the constitution at the
start, would have saved time? Look specifically for:

- **Commands** discovered or corrected (build, test, dev, lint, deploy, migrate)
- **Gotchas** — ordering dependencies, prerequisites, "delete X if Y" recovery steps
- **Environment / config quirks** — required vars, flags, version pins
- **Codebase patterns** that were not obvious from a first read

If none of these came up, stop here and tell the engineer there is nothing worth
capturing.

### Phase 2 — Decide destination (canonical vs shim vs personal)

**Resolve the constitution first**, the same way `instructions-audit` does: it is
`AGENTS.md` when that file exists, is not a generated summary (no `Auto-generated by
MTK` marker in its first 10 lines), and `CLAUDE.md` is absent or a shim with a bare
`@AGENTS.md` line; otherwise it is `CLAUDE.md` (a **legacy** repo). In a legacy repo
every "canonical" row below means `CLAUDE.md` — never a generator-marked `AGENTS.md`,
whose next regeneration would discard the addition. Do not migrate as a side effect of a
capture: inversion is `/mtk-setup`'s job, proposed through the regen-diff contract.

| Destination | When |
|---|---|
| The resolved constitution (`AGENTS.md`, or `CLAUDE.md` in a legacy repo) | Project facts every contributor and agent benefits from, regardless of harness |
| `CLAUDE.md` / `GEMINI.md` shim | A fact genuinely specific to that one harness (rare — most facts belong in `AGENTS.md`) |
| `.claude.local.md` (gitignored, personal) | Your own preferences, local-only paths, machine-specific setup |

Heuristic: first-person preference ("I like to run…") → personal. Project fact
("tests must run with `--runInBand` due to shared DB state") → the resolved constitution. A
harness-only quirk (e.g. a Claude Code `instructionFiles` mode note) → the
shim's own short section, not `AGENTS.md`. When in doubt, propose it as
personal or as an `AGENTS.md` fact, never as a shim addition.

For monorepos, prefer the **nearest** package `AGENTS.md` (or `CLAUDE.md`
where a package has not yet migrated) when the fact is local to one package;
only put cross-cutting facts in the root file.

### Phase 3 — Check for duplicates

Before drafting, grep the target file (and `tasks/lessons.md`) for the keyword.
If the fact is already documented, do not re-add it — update the existing line
only if it is now wrong.

```bash
grep -in "<keyword>" AGENTS.md CLAUDE.md .claude.local.md tasks/lessons.md 2>/dev/null
```

### Phase 4 — Draft additions (concise)

One line per concept. The constitution is part of the prompt — brevity is the
whole point. Format: `` `<command or pattern>` — <brief description> `` and
match the existing file's style (table vs bullet list — do not impose a new
structure).

Avoid: verbose explanations, restating what the code already says, generic best
practices, and one-off fixes unlikely to recur.

Mind the budget: `AGENTS.md` targets 60–80 lines with a hard cap of 120 — the
same budget `setup-bootstrap` generates against and aborts above; a `CLAUDE.md`
shim's cap is 20 lines. If an addition would push either over budget, propose moving detail
to the relevant `.claude/rules/` file instead, or drop the lowest-value
candidate. The proposal must also pass the relative gate —
`bash scripts/growth-gate.sh AGENTS.md <proposed>` (or `CLAUDE.md` when the
target is the shim) — because a capture pass that grows the file a few
percent every session ratchets the always-loaded context until the absolute
cap finally trips.

### Phase 5 — Show proposed changes (no edits yet)

**Stop before any edit.** For each candidate, show where it goes, the diff, and
one line of why it helps future sessions.

```
### Addition 1 → ./AGENTS.md (Gotchas section)

**Why:** Tests silently corrupt each other without --runInBand; future sessions
would re-discover this the hard way.

\`\`\`diff
+ Tests must run sequentially (`pytest --runInBand`) — shared DB state.
\`\`\`
```

Then ask: **"Apply these? (yes / partial / no)"**

### Phase 6 — Apply with approval

After explicit approval, apply with `Edit` (never `Write`). Append into the
relevant section; never restructure. If the engineer approved "partial", apply
only the named subset. If a personal item was chosen and `.claude.local.md` does
not exist, create it (it is gitignored by `setup-bootstrap` — verify it is
listed in `.gitignore` before creating; add it if missing).

## Rules

- **Never apply before approval.** Phase 5 output is a proposal, not an edit.
- **Append over rewrite.** New facts go at the end of the relevant section.
- **Use `Edit`, never `Write`** on `AGENTS.md` or `CLAUDE.md` (S1.5
  protected-file rule).
- **One line per concept.** If you need a paragraph, it belongs in `.claude/rules/`.
- **Match the file's existing style.** Do not impose a template.
- **Default to `AGENTS.md`.** A shim addition is the exception, not the norm
  — most "should this go in CLAUDE.md" instincts are really "this belongs in
  AGENTS.md".
- **No manufactured additions.** "Nothing to capture" is a valid, common outcome.

## Common Rationalizations

See `.claude/references/workflow-rationalizations.md` for the shared MTK table.
Capture-specific traps:

- **"I should add a few things so the session feels productive."** No. Capture
  only what was genuinely surfaced. Empty output beats noise in the prompt.
- **"This gotcha is obvious."** If you had to discover it this session, it was
  not obvious to a cold-start agent — capture it.
- **"I'll rewrite the Commands section to be cleaner while I'm here."** No. That
  is `instructions-audit`'s job, gated on its own rubric. Capture appends; it does
  not refactor.
- **"This is a personal preference, but the team file is easier."** Default
  personal. Promotion to the team file is the engineer's explicit call.
- **"This is Claude-specific, so CLAUDE.md is the obvious place."** Usually
  not — a shim addition should be rare. If it applies to any agent reading
  the constitution, it belongs in `AGENTS.md`.

## Red Flags

- Additions applied before the engineer approved them
- A whole-section rewrite proposed instead of an append
- Generic best practices ("write tests", "use good names") added as if
  project-specific
- `AGENTS.md` pushed over its 120-line hard cap, or a `CLAUDE.md` shim pushed
  over its 20-line budget, by the additions
- `.claude.local.md` content committed (it must stay gitignored)
