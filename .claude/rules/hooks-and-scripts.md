# Hooks & Scripts (S3)

> Generated by init on 2026-04-11. Cite rules as S3.N in reviews.

## Bash Standards

- **S3.1** All bash scripts must start with `#!/usr/bin/env bash` and `set -euo pipefail`.
- **S3.2** Hook scripts must be executable (`chmod +x`).
- **S3.3** No external dependencies beyond coreutils, grep, sed, awk, find, git. The toolkit must work on a fresh macOS or Linux machine. Opt-in features may probe for an extra tool (e.g. openssl for release signing) but must degrade gracefully — never a hard failure — when it is absent or lacks the needed capability (stock macOS LibreSSL has no Ed25519). python3 is part of the accepted baseline (macOS and mainstream Linux ship it); scripts may hard-require it with a clear exit-2 message.
- **S3.4** Use `"${VAR:-}"` for optional environment variables to avoid unbound variable errors under `set -u`.

## Hook Configuration

- **S3.5** Plugin hooks are defined in `hooks/hooks.json` under the `hooks` key. Settings hooks are in `.claude/settings.json` under `hooks`.
- **S3.6** Plugin hooks (`hooks/hooks.json`) are the whole runtime, with `${CLAUDE_PLUGIN_ROOT}` paths so it runs in plugin-installed repos. Exactly these are registered: `SessionStart` (`startup|clear|compact|resume`) → `session-start`; `PreToolUse` `Bash` → `security-gate.sh` (destructive commands, plus the S4.12 interactive-prompt check), `format-on-edit.sh --flush-before-verify` and `push-gate.sh` (registered with `"if": "Bash(git push *)"` so it runs only on `git push`; checks the pushed range against a diff-bound review receipt; advisory by default, `MTK_PUSH_GATE_ENFORCE` selects `off|advisory|shadow|active`); `PreToolUse` `Edit|Write` → `scope-guard.sh` and `config-guard.sh`; `PostToolUse` `Edit|Write|Bash` → `evidence-ledger.sh` and `context-guard.sh` (`timeout: 5`; telemetry to `.mtk/sessions/<session>/telemetry.json` only when `.mtk/` is git-ignored; one `additionalContext` nudge per workflow step at `MTK_CTX_SOFT`/`MTK_CTX_HARD`, a generic one per 150k band from `MTK_CTX_GENERIC` without a workflow; a throttled call starts no python; `MTK_CONTEXT_GUARD=0` disables); `PostToolUse` `Edit|Write` → `spec-approval-trigger.sh` and `format-on-edit.sh`; `Stop` → `verify-completion` and `format-on-edit.sh --flush`, plus the async `workflow-continuation.sh` and `cost-tracker.sh` (session cost and `.claude/analytics.json`); `SubagentStart` → `subagent-context.sh` (context only, never blocks); `PostCompact` → the async `compact-archive.sh` (archives the compaction summary to `.mtk/sessions/<session>/`, mode 0600, only when `.mtk/` is git-ignored; `MTK_COMPACT_ARCHIVE=0` disables; the retired name `post-compact.sh` stays banned by the wiring test). Every registered hook stamps its liveness under its own file name (`mtk_hook_seen <file name>`, right after sourcing `hooks/lib/hook-io.sh` or after its kill-switch), and `validate-toolkit` FAILs on one that does not. `hooks/lib/hook_registry.py` is the one parser of the registered handlers (script, args, matcher, `if`, timeout, rarity) read by the production readers (`validate-toolkit`, `mtk-doctor`) and the wiring test (other tests may read `hooks.json` directly as independent oracles); `if`-filtered, `SubagentStart` and `PostCompact` handlers are event-rare, so the doctor reports a missing stamp on them as info, not a WARN. The wiring test also pins the `if` filter, which its command table does not read. No hook runs on `UserPromptSubmit`, `PreCompact`, Read/Grep/Glob or MCP calls — any matcher naming `mcp__` counts — and `validate-toolkit` and `mtk-doctor` both FAIL if one is added, through one shared classifier (`hooks/lib/hot_path_matchers.py`); model-visible text goes out as `additionalContext`, since stdout/stderr on exit 0 is not shown to the model. The plugin is their only registration: `.claude/settings.json` wires no MTK hooks, including in this dev checkout, which runs the working tree as the plugin via `claude --plugin-dir .`. Wiring a hook in both places makes it fire twice per event, and there is no in-hook guard against that. Everything else under `hooks/` is on-demand, never registered: the scripts `ci-status`, `collateral-guard`, `check-prerequisites`, `parse-build-diagnostics`, `pre-commit-linters` and `merge-settings`; the data directories `analyzer-severity/` (read by `parse-build-diagnostics`) and `linter-patterns/` (read by `pre-commit-linters`); `git-hooks/` (installed into a repo's own git hooks by setup); and the sourced helpers in `lib/` (`hook-io.sh`, `guard-mode.sh`, `shrink-guard.sh`, `gate-backstop.sh`, `mtkignore.sh`, `hook_registry.py`, `active_workflow.py`, `hot_path_matchers.py`, `session_store.py`).
- **S3.7** The verify-completion Stop hook reads the Stop payload from stdin and checks the transcript's final completion claim for evidence keywords. It skips a completion claim only when it positively knows nothing changed: no recorded edit, and the working-tree fingerprint still equals the baseline recorded before the session's first tool call. A missing ledger, baseline or `session_id`, or a fingerprint that cannot be computed, falls through to the gap checks (fail closed). Evidence is bound to the verified tree: `evidence-ledger.sh` stores a tree fingerprint with each verification command, and a different fingerprint at Stop re-arms the gap however the files changed (outside git it falls back to edit/verification sequence numbers). Ledger state is keyed on the payload's `session_id`. On a gap it blocks the stop once (`decision: "block"` with a VERIFICATION GAP reason) so the model restates fresh evidence; it never blocks when `stop_hook_active` is set, and stays silent otherwise.
- **S3.8** Session-start hook must support multiple platforms: Claude Code, Cursor, Copilot CLI, Gemini CLI.
- **S3.11** On a `compact` SessionStart (the payload's `source`), `hooks/session-start` re-injects on-disk state the compacted conversation lost: tech stack, active spec/plan, incomplete tasks, a recent handoff artifact and at most one workflow. Paths resolve against the project root (specs and plans against the artifact root, S1.16), never the hook's cwd. Only the newest workflow whose status is `active` and whose `updated_at` is within 7 days (`MTK_WORKFLOW_REINJECT_DAYS`) is re-injected. The handoff is filtered by `scripts/handoff-state.sh` frontmatter: the newest note that is `open`, or `accepted` during this session (approximated as within 24 hours), and whose `branch` is the current branch; a legacy note without frontmatter, and a frontmatter note with no `branch`, count only when modified < 24h (a branchless note is never offered on `startup` or `clear`). When the script is absent or fails, the hook falls back to the first `docs/handoffs/*.md` modified < 24h. The block rides in the same `SessionStart` `hookSpecificOutput.additionalContext` envelope as the session context, framed as reference, not instruction — no blocking, no side effects. Other sources (`startup`, `clear`, `resume`) get no recovery block; `startup` and `clear` may carry exactly one `HANDOFF OFFER:` line, appended after any `SESSION RECOVERY` line, when an `open` handoff names the current branch (never the `POST-COMPACTION` token). When the offered note names an active workflow (`workflow:` frontmatter), the same message carries one `RESUME (offer, not instruction):` segment — built by the hook from `workflow-artifact.sh resume <uuid> --offline --porcelain` (key=value lines parsed in bash, read-only, no `gh`; the human output is never parsed) as `<uuid> (<type>, <phase>) — note: … | drift: … | next_command: … | needs_user: N open question(s)`, capped at 600 chars; any failure appends nothing. An open note whose `workflow:` names an existing workflow that is not `active` (completed, abandoned) is not offered at all (no `HANDOFF OFFER`, no `RESUME`); an unknown workflow or a note without the key keeps the plain offer. When no handoff is offered, `startup` and `clear` may instead carry at most one `COMPACTION OFFER:` line naming the newest `.mtk/sessions/*/compact-*.md` archive whose `branch` is the current branch and whose mtime is within 24 hours — a path, never summary text. On `startup` only, the hook also prunes `.mtk/sessions/*` directories older than 14 days through `hooks/lib/session_store.py`, gated like the writers (`.mtk/` git-ignored, or no git); `compact` never prunes.

## Shrink-Guarded Writes

- **S3.16** Protected artifacts that get regenerated (`architecture-principles.md`, `references.index`, in-place rewrites of `tasks/lessons.md`) must be written through `mtk_guarded_write` from `hooks/lib/shrink-guard.sh`. The helper refuses writes that shrink the target by > 50% bytes or > 20% lines. Override with `MTK_SHRINK_GUARD_OVERRIDE=1` for intentional rewrites. Pure appends are exempt — they cannot shrink.

## SIGPIPE Under Pipefail

- **S3.17** Never pipe into an early-exiting consumer (`grep -q`, `head`, `grep -m`) under `set -euo pipefail`: the consumer exits on its first match/line, the producer takes SIGPIPE (exit 141), and pipefail turns that *success* into a failure that blames a random innocent input per run — or, inside `$(…)` under `set -e`, kills the script exactly when the branch is needed. Five live instances were found and fixed in Aug 2026 (validate-toolkit reference scan, test-interactive-guard #17, generate-agents-md ×2, test-query-code-index). Use `grep -q PATTERN <(producer …)` (process-substitution exit is ignored), `awk 'NR<=n'` instead of `| head`, or a bash `case` match on a captured variable. Piping into a consumer that reads all input (`wc`, `sort`, `awk` without `exit`) is safe.

## Security-Gate Floor

- **S3.18** `hooks/lib/gate-backstop.sh` is a floor. It holds the 8.0.3 destructive-command patterns, which run before the token checks, and a deny from either layer wins. Never weaken or remove a backstop pattern to fix a false positive. Strip the false-positive text instead (only git/gh message values and the heredocs that feed them are stripped). `tests/hooks/test-security-gate-superset.sh` fails on any probe the 8.0.3 gate denied and the current gate allows, so add a probe to `tests/hooks/fixtures/security-gate-superset.cases` for every new bypass found. The gate is a drift control against accidental destructive commands, not a sandbox; native `permissions.deny`/`ask` (bootstrap baseline) carry the hard boundaries.

## Validation Script

- **S3.9** `scripts/validate-toolkit.sh` is the gate. It checks: required files exist, versions match, frontmatter present, skill anatomy valid, manifest paths exist, README/CONTRIBUTING/AGENTS coverage.
- **S3.10** Any new required file or structural constraint must be added to the validation script.
