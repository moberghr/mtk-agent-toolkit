# Product Context Artifacts — product.md + decisions.md

Read this companion only when `setup-bootstrap` STEP 3.8 runs. It covers what
to write into each file and the generation rules that apply to both.

## product.md template

Target **≤40 lines**. Sources: the README/docs scan (STEP 2) plus interview
question 7 ("One sentence: what does this product do, and for whom?" —
`.claude/setup-answers.json` `answers.product_purpose`).

```markdown
# Product Context

> Auto-generated by setup-bootstrap. Describes what this product IS today —
> not the roadmap. Every claim below carries an evidence anchor.

## Purpose
[2-3 sentences. What does this product do? Evidence: engineer interview — .claude/setup-answers.json (product_purpose), or a README/docs path.]

## Users
[Who uses this, and their primary job(s)-to-be-done. Evidence: README/docs path, or engineer interview — .claude/setup-answers.json (product_purpose).]

## Key flows
- [3-6 bullets — the primary user-facing or system flows. Evidence: a file path per flow, e.g. `src/api/checkout/`.]

## Non-goals
[Explicit — what this product deliberately does NOT do. Evidence-backed only; omit the section entirely if the scan/interview surfaced nothing concrete. Do not invent one.]
```

**Generation rules:**
- **Sources only:** the README/docs scan and interview question 7. Never invent purpose, users, or flows the scan/interview didn't surface.
- **Evidence anchor per claim (MANDATORY):** every line carries a backticked file path or `engineer interview — .claude/setup-answers.json (product_purpose)`. Verification happens in STEP 3.8, immediately after generation — `scripts/verify-claims.sh` runs directly on the generated file, not via STEP 3.5a (which runs before `product.md` exists).
- **No-aspirational-rules bar applies:** document what the product IS, not what it's planned to become — same bar as CLAUDE.md's "Rules for Generation".
- **Never overwritten if present** — see the File Preservation Policy. Regenerating over an existing `product.md` on a later re-run routes through `.claude/references/regen-diff-contract.md` like any other MTK-owned doc.

## decisions.md template

ADR-lite, **append-only** — regeneration may only append new entries; it must
never rewrite, reorder, or delete a prior one.

Entry form:

```markdown
## YYYY-MM-DD — <decision>

**Context:** [why this decision was needed]
**Decision:** [what was decided]
**Evidence:** [commit SHA, file path, or interview key — e.g. `a1b2c3d`, `Directory.Packages.props`, or `engineer interview — .claude/setup-answers.json (hard_nevers)`]
```

**Seed sources (first generation only):**
- **Detectable history** — framework migrations and major version bumps found in `git log` (STEP 2's Git Conventions scan). Cite the commit SHA.
- **Interview rationale** — `hard_nevers` and `invisible_conventions` answers where the engineer gave a reason, not just a rule. Cite `engineer interview — .claude/setup-answers.json (hard_nevers)` or `(invisible_conventions)`.
- If neither source yields a concrete entry, seed the file with the header only and no entries — an empty decision log is correct; a fabricated one is not.

**Generation rules:**
- **Append-only, always.** A re-run may add new entries (new commits, new interview rationale) but must never edit, reorder, or remove an existing `## YYYY-MM-DD — <decision>` block.
- **Never overwritten if present** — same preservation contract as `product.md`.
- Evidence is mandatory per entry — a decision without a SHA, path, or interview key is not written.

## Shared rule: both files

Neither file is (re)generated if it already exists — bootstrap preserves it
untouched and reports it under "Preserved hand-authored files" (STEP 5). Both
writes go through the STEP 3.5c secret-scan gate before landing on disk.
