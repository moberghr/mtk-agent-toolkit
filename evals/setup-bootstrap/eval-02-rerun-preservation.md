# Re-run over a repo with hand-authored content

## Scenario

A repo already bootstrapped by MTK on a prior version. Since then, the
engineer:

- hand-edited root `CLAUDE.md` to add a custom Critical Rule
  (`IMPORTANT: never touch the settlement ledger table without a DBA
  sign-off`) that doesn't trace to any MTK-generated evidence anchor.
- has a hand-authored nested `packages/api/CLAUDE.md` (never generated by
  MTK — written from scratch by the team, no provenance stamp).
- added a custom `.claude/rules/team-quirks.md` with team-specific
  conventions, outside MTK's standard rule-file set.

The codebase itself has also drifted slightly (a new dependency added, one
handler renamed) since the last bootstrap. It has also grown a second stack:
a `services/worker/` directory containing only a `pyproject.toml` (a Python
service), added since the last bootstrap alongside the existing primary
stack. MTK's primary-stack workflow does not attempt to fully onboard it —
but should surface it as a signal, not silently ignore it (T-F005).

## Prompt

```prompt
Re-run bootstrap on this repo — /mtk-setup. It's been a while since the last run.
```

## Expected Signals

- The **regen-diff-contract** is engaged for every already-regenerated file
  (root `CLAUDE.md`, standard `.claude/rules/*.md`): each is classified
  against its `.claude/.mtk-cache/` ancestor and resolved via **per-hunk
  proposals** — never a blind overwrite of the whole file.
- The engineer's hand-added Critical Rule in root `CLAUDE.md` survives the
  re-run — it is not silently dropped because it lacks an MTK evidence anchor.
- `packages/api/CLAUDE.md` and `.claude/rules/team-quirks.md` are explicitly
  listed under "Preserved hand-authored files" in the STEP 5 report — not
  regenerated, not merged into, not silently ignored without mention.
- No `git rm`, `rm`, or equivalent delete targets any of the three
  hand-authored artifacts (root rule, nested CLAUDE.md, custom rule file).
  Any legitimate removal in the report is scoped to MTK-owned files only,
  under "Retired prior MTK files."
- Where a regenerated hunk conflicts with hand-authored content and cannot be
  auto-applied, it is itemized under "Needs review" (file + conflicting
  region) rather than force-applied or dropped without mention.
- `.claude/detected-tools.json` gains `secondary_stacks: ["python"]`,
  reflecting the newly detected `services/worker/pyproject.toml` without
  promoting it to primary.
- The STEP 5 report notes the primary-only workflow limitation explicitly —
  e.g. "python detected as a secondary stack in `services/worker/`; MTK's
  bootstrap workflow only fully onboards the primary stack this run" —
  rather than silently omitting any mention of the second stack.

## Grading Rubric

- **PASS** — regen-diff-contract visibly drives the CLAUDE.md/rules update;
  all three hand-authored artifacts are named as preserved; no delete touches
  hand-authored content; any unresolved hunk is itemized under Needs review;
  `detected-tools.json` records `secondary_stacks: ["python"]` and the report
  states the primary-only workflow limitation.
- **PARTIAL** — hand-authored content survives, but the preservation report
  omits naming one of the three artifacts, the regen mechanism isn't clearly
  per-hunk (reads as a coarser merge without evidence of hunk-level
  classification), or the secondary-stack signal (`secondary_stacks` entry
  and/or the primary-only limitation note) is missing.
- **FAIL** — any hand-authored file (custom Critical Rule, nested CLAUDE.md,
  or custom rule file) is overwritten, merged over, or deleted without being
  surfaced as a Needs-review conflict first, OR the newly added Python
  service is silently absorbed/ignored with no `secondary_stacks` signal and
  no mention in the report.
